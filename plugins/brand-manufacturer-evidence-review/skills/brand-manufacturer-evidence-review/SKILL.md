# 品牌与制造商证据复核

电商页面以商业品牌和商品名组织，企业、商标、专利等调查对象则按法律主体组织；商业名称不能替代法律主体。为使结论可复核和复用，需要保存准确法律名称、司法辖区、角色、当前/历史状态、证据及适用限制。

读取原始客户材料，登记 `SRC-xxx` 来源，提取产品、商品和目标品牌；按照 [证据复核规则](references/review-rules.md) 调查并构建符合 [JSON Schema](references/evidence-review.schema.json) 的草稿。

调查必须实际执行网络检索：至少使用一个官方登记/监管数据库和一个目标品牌或产品官方页面，并在 `网络检索记录` 中记录检索词、入口、时间、结果和失败原因。不得仅凭用户截图、搜索摘要、模型记忆或已有报告补写“已确认”事实；网络不可用时，只能输出“证据不足/待核实”。

可选使用 `scripts/tavily_search.py` 增强检索。仅当环境变量 `TAVILY_API_KEY` 已配置时调用；未配置时继续使用现有官方来源流程。Tavily 用于发现第二来源、历史页面、产品 PDF、收购公告和 Manufacturer/Importer 线索，不是证据等级来源。将其结果写入 `网络检索记录` 时标记 `来源引擎: Tavily`，并在形成 `EVD-xxx` 前回到原始页面或官方文件核验。每个品牌复核结果必须用 `检索记录引用` 回指实际用于该品牌的 `WEB-xxx`；只有引用中至少一条记录的 `来源引擎` 明确包含 Tavily 时，该品牌的 `实际查询路径` 才能声称使用 Tavily。不得把一个品牌的 Tavily 记录套用到其他品牌。适配器使用标准库，不要求额外安装 Tavily SDK；未配置密钥、网络超时或 API 错误时保留失败原因并继续按“证据不足/待核实”处理。

每条关键主张必须形成 `主张 → EVD-xxx → 原文摘录/页面定位 → 证据等级 → 结论状态 → 适用限制` 闭环。每个代表性 SKU 必须逐项记录包装/铭牌、型号或 UPC、说明书 Manufacturer/Importer、平台字段、合规或监管文件的核验状态；缺失项必须显式记录为未取得，并计算 `证据完整度`。商标权利人、当前运营主体、制造商等关键主张原则上需要两个独立来源交叉验证；只有单一来源时不得评为高可靠性。

关键关系的“已确认/高可靠性”门槛是至少两个独立来源域名；Tavily 结果、搜索摘要、Marketplace、Amazon、经销商页面不计入该门槛。代表性 SKU 证据完整度低于 2/7 时，具体 SKU 制造商只能写“候选/证据不足”，不得写成“已确认/高可靠性”。

最终 JSON 必须包含由 `scripts/quality_summary.py` 根据同一份事实自动计算的 `质量摘要`。每个品牌至少记录主要来源数、独立来源域名数、关键角色覆盖、SKU 证据完整度、冲突数和待补证数；总体记录品牌数量、冲突数和待补证数。不得手工改写摘要以掩盖质量缺口。DOCX“报告说明”只显示总体简版指标。

首次响应必须直接输出一份完整的中文调查报告，至少包含调查事项、证据范围、品牌/商标权利人、运营主体、母公司或控制主体、制造商/生产商、证据等级、结论、限制与后续核实建议。证据不足的字段不得省略，须明确写“证据不足/待核实”并说明原因。

每个新任务的首次响应必须在上述调查报告之前单独输出 `Skill 版本：<version>`。`<version>` 必须读取本插件 `.codex-plugin/plugin.json` 的 `version`，不得凭记忆或手工猜测；同一任务后续因修改而重述报告时无需重复该行。最终 JSON 顶层必须写入同一版本的 `Skill版本` 字段；该字段与表示数据规范的 `规范版本` 不同。DOCX 渲染器会在“报告说明”中同时展示这两个字段。

报告正文采用结果导向写法：只写事实、证据、判断、适用范围、冲突、限制和补证要求。不得出现“我搜索了……”“先查……再查……”“执行步骤”“查询路径”“模型认为”等过程性语句。检索词、访问记录、数据库访问、来源引擎和失败原因仅写入 JSON 底稿的审计字段，不在 DOCX 正文或章节标题中展开成过程叙述。DOCX 中的来源表只保留证据日期、来源、支持结论、证据等级、原文摘录和页面定位等结果信息。

报告正文结束后必须单独输出以下确认区块，不得以隐含语气结束：

> **请确认报告内容**
> 以上调查报告是否确认无误？请回复“确认生成文件”，或指出需要修改的事实、主体、证据或表述。

只有用户明确回复确认（例如“确认生成文件”）后，才写入最终 JSON 并生成 DOCX。用户未确认时，不得声称已生成最终文件；用户提出修改时，先修订报告并再次显示该确认区块。

运行 `scripts/check_runtime_dependencies.py` 检查运行依赖。如果缺失依赖，先按其输出的命令从 `requirements-runtime.txt` 安装；然后使用 `scripts/validate_evidence_review.py` 校验最终 JSON。校验通过且用户确认一致后，使用 `scripts/render_evidence_review_report.py` 仅从该 JSON 生成 DOCX，并逐页渲染检查。渲染失败或未完成逐页检查时，不得声称 DOCX 已通过质量验收。

用户确认后的最终交付：

- `outputs/<项目或品牌范围>_品牌权属与制造商证据底稿_<YYYYMMDD>.json`
- `outputs/<项目或品牌范围>_品牌权属与制造商证据复核报告_<YYYYMMDD>.docx`

文件名必须由以下确定性算法生成，不得根据正文标题自由改写：

1. `<项目或品牌范围>`：有客户项目名时使用项目名；没有项目名时，读取 `调查范围.目标品牌`。仅 1 个品牌时使用该品牌的“规范名称”（例如 `VEVOR`）；多于 1 个品牌时使用 `N品牌`（例如 `十品牌`）。不得把“主体”“制造链条”“尽调”等自行加入范围名。
2. `<YYYYMMDD>`：取 `报告信息.调查日期`，删除 `-`，必须是 8 位数字。
3. 范围名含 Windows 禁止字符 `\\ / : * ? " < > |`、首尾空格或句点时，视为非法输入并停止生成；不得静默替换。JSON 与 DOCX 必须使用同一范围名和日期。
4. 固定中缀只能是 `品牌权属与制造商证据底稿` 或 `品牌权属与制造商证据复核报告`，禁止使用“尽调报告”“制造链条报告”等替代词。
5. 同一范围、同一调查日期重新生成正式交付物时覆盖同名文件，不追加随机编号。

生成前必须运行 `scripts/check_output_filename.py` 校验两个输出路径；校验失败时不得生成或声称生成文件。该脚本同时检查 JSON/DOCX 的范围名和日期是否一致。

示例：`outputs/十品牌_品牌权属与制造商证据复核报告_20260813.docx`。
